Methodology & data audit notes

How every figure on the dashboard is sourced and calculated. Raw rows behind these calculations are in data.html.

2. Electricity KPI cards (DE / NL / BE / LU)

Value shown

Each country's card shows its average load (in GW) for the most recent day with complete data — this is a straight average of that day's hourly MW readings from ENTSO-E, converted to GW (÷1000).

"vs 30d avg"

The percentage compares that latest-day value against the plain average of the trailing 30 days: pct = (latest − avg30) / avg30. The GW figure in parentheses next to it is that 30-day average itself, so you can see both the reference number and the deviation.

Sparkline

The colored line is the daily average load for each of the last 30 days, plotted with no smoothing (raw daily values). The grey dashed line is the flat 30-day average from the same window, so you can see at a glance whether the country is currently running above or below its own recent norm. The "low / high" figures underneath are the minimum and maximum daily values in that 30-day window.

3. Gas pipeline KPI cards (Norway / Algeria / Azerbaijan)

Same logic as the electricity cards, but in GWh/day instead of GW, and the value for a given day is the sum across all tracked entry points for that origin country (see the point list below). ENTSOG reports flow in kWh/day; the dashboard converts to GWh/day by dividing by 1,000,000.

OriginEntry points summed
NorwaySt Fergus (UK), Easington (UK), Dunkerque (FR), Zeebrugge (BE), Emden EPT1 (DE)
AlgeriaAlmería (ES, via Medgaz), Mazara del Vallo (IT, via Transmed)
AzerbaijanKipoi (GR) — the TANAP→TAP handover point on the Greek border, used as a proxy since Azerbaijan has no direct pipeline border with the EU
This is a curated list of the main, unambiguous physical entry points — not every commercial sub-point ENTSOG lists — chosen to avoid double-counting the same physical gas flow twice. If your boss wants a different or more complete point list, it's a one-line change in scripts/fetch_entsog.py.

4. Demand chart (all 4 countries)

Same daily average load figures as the KPI cards, plotted as one line per country. No smoothing is applied — demand is naturally smooth day to day, so raw values are shown as-is.

5. Renewable share chart

For each country and day: renewable share % = (sum of MW from renewable fuel types) / (sum of MW from all fuel types) × 100. Fuel types counted as renewable: solar, wind (onshore & offshore), hydro (all types), geothermal, biomass, and other renewable. This raw daily series is noisy (weather-driven), so the chart applies a 7-day trailing rolling average — each plotted point is the average of that day and the 6 days before it — to make the underlying trend readable instead of a jagged line.

6. Generation mix donut

Uses only the most recent day with complete generation data, summed across DE + NL + BE (Luxembourg has no generation data in ENTSO-E — it's a load-only market). The 6 largest fuel types by MW are shown individually; everything else is grouped into "Other" so the chart stays readable instead of showing all ~14 raw fuel categories. Percentages are of that day's combined total.

7. Net cross-border flow chart

For each country and day: net flow = (MW exported to all neighbours) − (MW imported from all neighbours), using ENTSO-E's physical cross-border flow data. Positive = net exporter that day, negative = net importer. Also smoothed with a 7-day trailing rolling average, same reasoning as the renewable share chart.

8. Gas import flows chart

Same origin-level daily totals as the gas KPI cards, plotted as one line per origin country, also smoothed with a 7-day trailing rolling average.

9. Known limitations

ENTSO-E occasionally publishes incomplete or delayed data for the most recent 1-2 days; the dashboard always uses the latest day that has a complete set of hourly points, which may be "yesterday" rather than "today" depending on when you check. ENTSOG data has no equivalent gap so far. Timezone: all "daily" buckets are calendar days in Central European Time (Europe/Berlin), not UTC, to match how a Frankfurt-based reader would think about "today's" data.
